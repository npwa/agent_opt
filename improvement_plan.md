- **M2 steps 2+3 done (2026-10-19):** `harness/telemetry.py` (NVML sampler at 10 Hz: utilisation, memory, power, SM/mem clocks, PCIe via a separate thread because that NVML call takes ~40 ms; CPU/RAM at 1 Hz; `GpuSamples` window lookup, half-open windows) and `harness/trace.py` (`python -m harness.trace --run <out>`: per-trial `trace.json` joining OpenCode events, proxy records incl. new `chunk_t` arrival offsets for ITL p50/p99, and GPU samples; mismatches are reported as `warnings`). Runner starts the sampler (`--gpu-hz`, `--no-gpu`). A real recorded trial is committed as a replay fixture (`fixtures/traces/coding_05_real`).
  **Measured on the 3080:** sampler vs `nvidia-smi dmon` over 165 s: 62.5 % vs 62.8 % mean utilisation (0.3 pp; acceptance ±5 pp). **Learned:** (a) OpenCode stamps `step_start` at the *first token*, not at request start - its offset from the proxy start equals the proxy-measured TTFT, so the join checks `t_start + ttft` (and gets a free cross-check of TTFT); (b) on these tasks tool execution is milliseconds and the gap between LLM calls is < 0.3 s, so the GPU idle-while-tools-run story will be weak for this suite (the long tasks are LLM-bound; GPU utilisation during LLM calls is only 30-60 % because 2/3 of the model is offloaded to CPU); (c) NVML utilisation is a coarse "any kernel active" signal.

- **M2 step 4 done (2026-10-19):** `harness/decompose.py` (`python -m harness.decompose --run <out>`, after `harness.trace`): wall = prefill + decode + tool + harness (+ start-up/between/shutdown parts) + unattributed, per trial and time-weighted per task category (`decomposition.json/.md`), plus GPU duty cycle, utilisation during prefill vs decode windows, and energy. The unattributed bucket becomes non-zero only when the join is inconsistent (overlapping LLM windows, clock skew, OpenCode steps without a proxy record); a trial is flagged unless it is < 5 % and LLM overlap < 1 %. **Acceptance met on two real recorded trials** (both fixtures committed; unattributed ≈ 0 %, harness 2-4 %, no warnings).
  **Finding to carry into M5:** on the real runs 73-79 % of wall-clock is prefill (TTFT). Almost all of it is the *first* call of a session: ~10k tokens of system prompt + tool schemas, processed at ~250 tok/s on the CPU-offloaded model (≈ 40 s), with later calls hitting the prompt cache (2-3 s TTFT). Ollama's OpenAI endpoint does not report load time, so model loading and uncached prefill cannot be separated (the report gives the first call on its own). This supports the prompt-budget hypothesis (F13) and says tool-schema trimming is worth more than decode tuning on these tasks.

- **M2 step 5 done (2026-10-19):** `--parity-fraction` in the runner adds `ceil(fraction × n)` uninstrumented trials per (config, task) cell (OpenCode straight to Ollama, no proxy; ids `…__p00`); `analysis/parity.py` (`python -m analysis.parity --run <out>`, also printed at the end of a run) compares them with the instrumented trials of the same cells: time = pooled geometric-mean ratio with bootstrap CI (violation / ok / inconclusive against ±5 %), success = Wilson intervals (violation if they do not overlap); `analysis/stats.py` has the Wilson/bootstrap helpers (tested against scipy). Trace/decomposition skip uninstrumented trials.

- **P8 done (2026-10-21, CPU only, uncommitted until reviewed):** `harness/promptbudget.py` (`python -m harness.promptbudget --run <dir> [--request body.json]`, 6 tests; writes `promptbudget.md/json`), applied to the baseline (`results/v1/baseline/promptbudget.md`). The component budget comes from a real first-call request captured by running OpenCode against a local **stub server** (no model, no GPU); the raw body is not committed (it contains local paths).
  **Findings:** (1) cold prefill runs at **250 tok/s in all 140 trials** (min 237, max 253); a 10.1k-token first prompt costs 40.6 s. (2) Follow-up calls fit `ttft = 1.10 s + new tokens / 250` (median error 0.25 s) and 97 % of their prompt is served from cache. (3) **No prefix reuse between trials**: first calls run at the cold rate even when the same task runs twice in a row (10 cases) - so every trial pays ≈ 40 s, 5 677 s of the 17 280 s measured (33 %) - although the prompt is mostly identical across trials; the per-trial working directory and date sit at character 8 692 of the system message, so at most the base prompt (22 %) is a guaranteed shared prefix, but we do not yet know why even that is not reused (needs a GPU probe, P12). (4) **Prompt components** (first call, ≈ 10.1k tokens): tool schemas 51 % (`bash` 1.3k tokens, `task` 1.0k, `todowrite` 0.7k), skills list 26 %, base system prompt 22 %, environment 1 %. (5) **Isolation leak:** the system prompt lists 12 skills read from the author's `~/.claude/skills` (including personal ones), so baseline prompts depend on the machine; `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1` (or `OPENCODE_DISABLE_EXTERNAL_SKILLS=1`) removes them (system message 19.3k → 9.6k characters, about 2.4k tokens = ≈ 10 s of cold prefill per trial). Correction: the earlier "first call ≈ 39 % of wall-clock" was a miscalculation; measured 33 %.
  **Consequence for H1 (prediction to test in M5):** prefill is linear in new tokens at 250 tok/s, so every 1k prompt tokens removed saves ≈ 4 s per trial; dropping the skills list (2.6k) and the unused `task`/`todowrite`/`skill`/`webfetch` schemas (2.1k) would save ≈ 19 s of the 123 s average trial (≈ 15 %).

- **P1 done (2026-10-21, CPU only):** `analysis/claims.py` (`python -m analysis.claims --run <dir>` → `claims.md/json`; 17 tests): finds verification claims in the agent's text ("tests pass", "verified", "compiles cleanly", ...; negated/future forms and fenced code ignored) and classifies the evidence before each claim from the OpenCode event stream: `supported` (last bash execution exited 0, no later edit), `stale`, `contradicted`, `unverified`. Evaluated on code-producing tasks only (code generation, bug fix, refactor). Applied to both baselines (60 trials each): **25 trials end with a claim in both runs; 24 of 25 are `supported`, 1 `unverified`, 0 stale/contradicted** - the v0 pattern "claims tests pass without running them" is rare here (1 of 25, CI 1-20 %). **False claims** (final claim but the hidden verifier fails): 5/60 = 8 % (CI 4-18 %) isolated, 2/60 = 3 % first run; almost all `c_ringbuf_03` (3 of its 3 claims): the agent's own compile-and-run succeeded but the sanitizer-based hidden tests fail. So the v0 regression is better described as over-claiming from weak self-checks than as claiming without running anything.
  **Consequence for H6:** a `coding` agent that mandates a verification step has little to fix on "unverified" claims (headroom 1/25); the useful target is claims made after a *weak* check. Measure: false-claim rate and the share of runs that compile with `-Wall -Wextra -fsanitize=address,undefined` before claiming; the checker needs a second evidence level for that (command-pattern based) when H6 is run. ## 3. Goals and non-goals

### Goals
G1. Turn the benchmark into a **statistically defensible evaluation** (n ≥ 10 per task, CIs, pass/fail verifiers).
G2. Explain **where time goes inside an agent run** (LLM prefill, decode, tool execution, harness overhead, GPU idle) and which knob fixes which part.
G3. Replace prompt-only citation hygiene with an **automated post-hoc citation verifier** (DIRECTION.md Stage 2).
G4. Test three **inference-side levers** specific to agent loops: prompt/prefix cache reuse + prompt trimming, KV-cache/`num_ctx` sizing, speculative decoding with a same-family draft model.
G5. Make the harness **self-testing** (unit tests, replay mode, fault-injection, CI) so results are trustworthy.
G6. Produce a **10-slide deck** and a README results dashboard.

### Non-goals
- No cloud-model fallback (keeps the original scope in `DIRECTION.md`).
- No Panther Lake / Arc validation (hardware not available); the plan keeps the platform
  abstraction (`platform.yaml`) so a future run is a config change.
- No model training/fine-tuning.
- Not a general agent benchmark (e.g. SWE-bench). The suite stays small and fully executable locally.

## 5. Design

```
 tasks/*.yaml ──► runner ──► OpenCode ──► metrics_proxy ──► Ollama / llama-server
                    │            │             │ (JSONL)            │
                    │            └ session export (tool events)     └ NVML sampler (10 Hz)
                    ▼                                               └ optional nsys capture
              trial JSONL ──► join (trace schema F5) ──► stats (bootstrap, tests)
                                                    ├─► citation verifier (F10)
                                                    └─► report/HTML (F14)
 replay: trial JSONL + fixtures replace everything left of "trial JSONL"
```

Key design choices:
- **Proxy stays a passive observer**: add a `--passthrough-bytes` mode that forwards raw bytes
  untouched and only timestamps chunks (removes the `stream_options` class of bug). Token
  counts come from Ollama's own final `eval_count`/`prompt_eval_count` fields, not request edits.
- **One event timeline per run** keyed by monotonic clock; wall-clock only for display.
- **Statistics:** percentile bootstrap (10 000 resamples) for medians and ratios; Mann–Whitney
  U for two-config comparison; Holm correction when several levers are compared; effect sizes
  reported alongside p-values. Success rate: Wilson interval.
- **Task specs and agent configs live in git** so every result maps to a commit.

### M5 — Lever experiments (revised 2026-10-21: screen, then confirm; ≈ 8-10 days incl. ≈ 25 h of unattended GPU time)

**Design.** *Stage A, screen:* every lever setting runs the **core suite** (tasks with a baseline pass rate of 30-90 %, plus two low-variance tasks and the new hard tasks; target ≤ 1.5 h) at n = 3-5. Screen results are *directional* (n < 5 is marked, nothing is claimed). *Stage B, confirm:* only levers that look promising, or that we intend to claim, are re-run on the full suite at n = 10 (≈ 5 h each) and judged by the §7.4 rule. The four always-pass tasks run at n = 3 in confirm runs as regression guards. *Prefill-only levers* (trimmed tool schemas, shorter agent prompt, KV settings) are first measured by **prompt replay** (P7), in minutes, then confirmed with a few full runs. One-factor-at-a-time from the baseline (32k, f16 KV, flash-attn on, default prompts); no full factorial.

**Hypotheses written down before running** (decision rules in §7.4):
- H1 (F13, revised 2026-10-21): trimming the tool schemas (68 % of the 7.3k-token prompt) / shortening the agent prompt cuts the *cold* first-call prefill by ≥ 20 % (≈ 6 s) but, with warm caches, total time by less than 5 %; it matters for new sessions and for the cache-miss cases (`comms_07`, `research_08e`), and must not lower success by more than 5 pp.
- H2 (F11, revised after the P4 survey): 16k keeps success; it moves the GPU/CPU expert split by one layer (30 → 29 on the CPU), so a speed effect is small; 8k breaks long-context tasks; 64k is needed by `research_08e` and costs time elsewhere.
- H3 (F11, revised): q8_0 KV cache saves 300 MiB at 32k (it buys back one expert layer, 30 → 29) at no measurable success cost; flash-attn off costs a layer (31) and is expected to be slightly slower.
- H4 (F11): `qwen3:8b`, fully GPU-resident, is faster per trial but passes fewer of the hard tasks.
- H5 (F12, revised after P9: built-in MTP / n-gram speculation, no draft model; smoke test: no speed-up at default settings, acceptance 60-86 % on copy-like output; the decode share is 60 %, but experts on the CPU limit the gain): speculative-decoding acceptance is higher on tool-call JSON than on prose; overall gain is small or negative because the draft model competes for VRAM.
- H6 (existing finding, revised after P1): the `comms` agent prompt still cuts calls (36 → 12); a `coding` agent that mandates a stronger verification step (sanitizers, edge cases) lowers the false-claim rate (baseline 5/60 isolated, 2/60 first run; "unverified" claims are already rare: 1 of 25).

**Screen budget:** ≈ 9 non-baseline settings × ≈ 1.5 h ≈ 13 h, confirm ≈ 2-3 levers × ≈ 5 h ≈ 10-15 h, so ≈ 25 h of GPU time instead of 35-40 h. If time runs short, cut in this order: second model, flash-attn, 8k.

1. **Context/KV sizing** (F11): `num_ctx ∈ {8k, 16k, 64k}` against the 32k baseline, KV `q8_0`, flash-attn off (needs P4); record VRAM, layers offloaded to CPU (Ollama log), decode tok/s, success. `research_08e` is in the core suite so the sweep itself decides the 64k question.
2. **Prompt-budget** (F13): tokens by component per call (P8); variants (a) default, (b) trimmed tool schemas, (c) shortened agent system prompt; confirm prefix-cache reuse via `prompt_eval_count`; replay-first, then confirm.
3. **Speculative decoding** (F12; redesigned after P9): no draft model - the target has built-in multi-token prediction (`--spec-type draft-mtp`) and llama.cpp offers n-gram speculation (`ngram-mod`, `ngram-map-k`); engine = Ollama's bundled `llama-server` with the CUDA backend path set (see `results/v1/spec_decode/README.md`). Sweep the draft length (`--spec-draft-n-max` 2-4 for MTP, `--spec-ngram-mod-n-max` 8-16) on **replayed agent outputs** (recorded requests, P7) split by output type (tool-call JSON, code written or edited, prose); report acceptance rate, decode tok/s and **output equivalence** against no speculation for every setting (two of four types already changed the greedy text in the P9 smoke test: such a setting is a different model configuration, not a free speed-up). Prediction to test: higher acceptance on structured/copied output than on prose (seen in P9) but little or no speed-up, because verification batches read many CPU-resident experts. Report the negative result if it occurs.
4. **Second model** (F11): `qwen3:8b` (P6), core suite at n = 5, confirm on the full suite if it is competitive; `llama3.1:8b` optional.
5. **Agent config**: re-verify the `comms` call reduction at n = 10 and add the `coding` agent variant with a mandatory verification step; measure false-verification claims with P1.

### 7.4 Experiment acceptance rules
- A lever is "positive" only if the 95 % CI of the improvement excludes 0 **and** success rate does not drop by more than 5 pp (Wilson, per task category).
- Every result table lists n; tables with n < 5 are marked "directional".
- Any surprising result must first be re-run with the uninstrumented path (rule already in `DIRECTION.md`).

### 7.5 Risks and mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
