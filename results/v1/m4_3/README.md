# M4.3: what share of the wall-clock is the GPU actually working? (2026-10-23)

`scripts/m4_3.sh`: 20 Nsight Systems captures, one trial each (`python -m harness.nsys capture`: a private, nsys-wrapped
Ollama, the metrics proxy and the runner on top, confined OpenCode, `qwen3.6` at 32k), two per task category (two different
cheap tasks where the category has two, otherwise the same task twice). The raw nsys files are deleted after each capture;
`RESULTS.md` (generated by `python -m analysis.nsys_summary`) has the tables, each capture directory the aligned summary and
the kernel summary. Nothing failed, no retries; 14 of the 20 trials passed.

## Answer to success criterion 4

* **The GPU is working 11.7 % of the wall-clock** (284 s of 2 420 s), and every category lies between 8.9 % and 13.0 %.
  Prefill is 55 % and decode 42 % of the wall-clock in these captures.
* **Inside the LLM windows the GPU is active about 9 % of the prefill time and 10-17 % of the decode time** (per category;
  short decodes at the low end). NVML, the coarse "any kernel in the sample window" signal of the earlier reports, shows
  37-83 % for the same windows: it overstates the real work by a factor of 3-8, most for the shortest tasks.
* **Why:** about two thirds of the model's expert weights stay in system memory (P4 survey), so the GPU computes in short
  bursts (median gap between bursts in decode 0.7 ms, p99 2.5-3.8 ms) and waits for the CPU in between; the processor,
  not the graphics card, is the bottleneck of this configuration, in prefill as well as in decode.
* The two captures of a category agree closely (e.g. `logtriage_04`: 12.2 % and 12.0 %), so the single-capture variance is small.

## Caveats

* One trial per capture, `qwen3.6` at 32k on this card only. Nsight cannot trace CUDA hardware events on this GPU/driver, so
  it uses a software-instrumented trace: durations carry some overhead, ratios are reliable (the pilot checked that 100 % of
  the kernel time lies inside the proxy's LLM windows).
* Each capture starts a fresh server, so the first call is cold (about 30 s of prefill), which raises the prefill share
  compared with back-to-back runs (33 % prefill in the isolated baseline once the cache is warm). The GPU-active
  fractions inside prefill and decode are not affected by that.
